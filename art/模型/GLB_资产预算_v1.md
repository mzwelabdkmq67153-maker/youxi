# 《第七竞技场》GLB 资产 / 显存预算 v1

- 工程根：`art\模型\glb\`
- 数据来源：`art\模型\glb\inventory.json`（脚本直接解析 GLB 实测，非估算）；本报告所有数字均可由 inventory.json 复算。
- 对比档位：**2K 原版**（`*_idle.glb`）与 **1024 降级版**（`*_idle_1024.glb`）。
- 渲染链路：three r128 UMD + 官方 `GLTFLoader.js`；`outputEncoding = sRGBEncoding`、ACESFilmic、曝光 0.80（见交接规范，未改灯光）。

## 1. 计算口径（可复算）

### 1.1 贴图解码显存

```
单贴图解码显存(B) = 宽 × 高 × 4(RGBA8 每像素 4B) × 1.33(mipmap 系数)
单贴图解码显存(MiB) = 单贴图(B) / 1024²
单模型贴图显存 = Σ 该模型全部贴图解码显存
场景贴图显存 = Σ 场上「唯一变体」模型贴图显存（同 URL 多实例共享，见 §3.2）
```

- 2048×2048：`2048² × 4 × 1.33 = 22,313,697.28 B ≈ 21.28 MiB / 张贴图`
- 1024×1024：`1024² × 4 × 1.33 = 5,578,424.32 B ≈ 5.32 MiB / 张贴图`
- 每份模型 3 张贴图（normal / baseColor / metallicRoughness，6 个材质槽共享同一组）：
  - **2K：21.28 × 3 = 63.84 MiB / 唯一模型**
  - **1024：5.32 × 3 = 15.96 MiB / 唯一模型**

### 1.2 包体与几何数据

- 文件字节：GLB 落盘总大小（JSON chunk + BIN chunk + 头）。
- 嵌入贴图字节：images 对应 bufferView 载荷之和（压缩态，下载/磁盘占用）。
- 几何/动画 BIN 字节：BIN chunk 扣除贴图载荷后的部分（POSITION/NORMAL/UV/JOINTS/WEIGHTS/INDICES/动画轨）；GPU 顶点缓冲量级与此相当，未另作显存折算。

## 3. 同屏场景显存预算

### 3.1 场景设定

- 主角 1 人；敌人分两档：**3 人** 与 **6 人**。
- 敌人从 swordsman / gunner / mage 三份 GLB 复用；场上唯一模型最多 3 份。
- 两种部署档位：
  - **全 2K**：主角与敌人全部加载 2K 版。
  - **敌人 1024**：主角保 2K，敌人加载 1024 版（独立 URL/变体）。

### 3.2 共享规则（计入显存的前提）

- 同一 URL 的模型经 `SkeletonUtils.clone` 克隆：**texture 与 geometry 引用共享，不重复占贴图/几何显存**；每个实例只持有各自的蒙皮姿态、变换与绘制调用。
- 敌人 1024 变体与主角 2K 变体是不同 URL，贴图**不跨档共享**；即便职业相同，敌人实例加载的是 1024 那份贴图。
- 下表只计**贴图解码显存**；顶点/骨骼缓冲按唯一模型计一次，实例增加不重复计算。

### 3.3 场景贴图显存表

| 场景 | 部署档位 | 唯一变体数 | 主角贴图显存 | 敌人贴图显存 | 合计贴图显存 | 唯一变体包体 (MiB) |
|---|---|---:|---:|---:|---:|---:|
| 主角 1 + 敌人 3 | 全 2K | 3 份唯一 GLB | 63.84 MiB（其中 1 份） | 127.68 MiB（2 份） | **191.52 MiB** | 11.181 |
| 主角 1 + 敌人 3 | 敌人 1024 | 1 份 2K + 3 份 1024 | 63.84 MiB | 47.88 MiB（3 × 15.96） | **111.72 MiB** | 9.810 |
| 主角 1 + 敌人 6 | 全 2K | 3 份唯一 GLB | 63.84 MiB（其中 1 份） | 127.68 MiB（2 份） | **191.52 MiB** | 11.181 |
| 主角 1 + 敌人 6 | 敌人 1024 | 1 份 2K + 3 份 1024 | 63.84 MiB | 47.88 MiB（3 × 15.96） | **111.72 MiB** | 9.810 |

复算示例（敌人 1024，1+3 / 1+6 相同）：
```
主角 2K：63.84 MiB
敌人 1024：3 × 15.96 = 47.88 MiB
合计 = 63.84 + 47.88 = 111.72 MiB
包体 = 最大 2K 主角文件 4,127,728 B + 三份 1024 文件 6,159,028 B = 10,286,756 B ≈ 9.810 MiB
```

## 5. 结论与临界点

### 5.1 结论：**「主角保 2K、敌人降 1024」成立。**

1. **主角保 2K**：主角是近景唯一高清视点，单份 2K 贴图解码显存 63.84 MiB，处于可接受区间；降到 1024 每份只省 47.88 MiB，但近景皮肤/布料/装甲细节损失明显，不划算。
2. **同屏多敌人必须降 1024**：场上 3–6 名敌人若全 2K，贴图解码显存最坏 **191.52 MiB**（3 份唯一模型）；敌人改 1024 后降到 **111.72 MiB**，省 **79.80 MiB（−41.7%）**，包体同步从 11.18 MiB 降到 9.81 MiB。在骁龙 680 一类共享显存档位，叠加场景贴图、UI、帧缓冲与后处理后，全 2K 偏紧，敌人 1024 是必要降级。
3. **实例数不推高贴图预算**：3 人 → 6 人敌人，贴图显存不变（同 URL 共享）；增长的是绘制调用数量与蒙皮算力压力，不在本贴图预算内。

### 5.2 临界点（按唯一模型数线性估算）

- 每增加一份**唯一 2K** 模型：贴图显存 **+63.84 MiB**；每增加一份**唯一 1024** 模型：**+15.96 MiB**。
- 全 2K 唯一模型达到 **3 份**即 191.52 MiB；达到 4 份将到 255.36 MiB，低配档不可接受。
- 建议部署规则：**仅主角加载 2K，其余出场模型（杂兵 / 远程兵 / 精英 / 首领变体）一律 1024**；后续若新增职业导致唯一模型数上升，远端与杂兵优先 1024，主角与近景精英再单独评估。
- 若后续要进一步压显存，可在不改几何的前提下评估：normal/MR 贴图降为更低分辨率、或按材质槽拆分贴图；本版未做。

## 6. 附注

- **色彩空间（GLTFLoader r128）**：baseColor / emissive 贴图被设为 `sRGBEncoding`，normal / metallicRoughness 等其余贴图按线性处理；本预算显存一律按 **RGBA8（4 B/px）** 计，不区分色彩空间。
- **已知模型侧缺陷**：枪手步枪左下碎屑、术士下摆内衬暗块，属模型资产问题，本档未在游戏侧用遮罩/贴图掩盖，仅在此登记（见交接规范 §5）。
- **未触碰项**：未改任何游戏 `.js` / `.html`；未做 git commit / push；未删除 `tripo_out` 原始素材与 2K 原版文件；`?art=ink` 水墨回退未改动。
- **复算方式**：`inventory.json` 含三模型两档的全部实测字段（文件字节、buffer/bufferView 字节、逐贴图尺寸/格式/嵌入字节、解码显存、三角/顶点/骨骼、动画、包围盒、材质与 emissiveFactor）；报告表格可由该 JSON 按 §1 公式重算。
